# DSMI 核心與驅動：混音、播放、輸出怎麼串起來

前一篇把 DSMI 的檔案分成介面、實作、非原始碼三類，這一篇走進去看執行時：
一個模組音樂檔從磁碟到喇叭，中間經過載入器、播放器、聲道分配器、混音器、
輸出驅動五層（檔與硬體本身不計層）。執行時資料路的邊界都是一張函式表，
呼叫方向永遠單向。

這裡先定義全文的地基名詞：模組（module）＝樣本＋樂譜。樣本（sample）是一小段數位錄音，
是樂器音色的單位；樂譜記載何時在哪一軌用哪個樣本、什麼音高、加什麼效果。
下文的「封存」指 DSMI 的原始下載包。

和前一篇一樣，這篇只讀原始碼。**DSMI 的授權禁止逆向該套件**，所以沒有反組譯、
沒有位元組簽章；給 remake 與逆向的辨認線索只到「原始碼層級的結構特徵」為止——
也就是原始碼裡直接可見的表形狀、常數、流程。結構特徵可以寫，
位元組簽章（要反組譯或比對機器碼才拿得到的）不行，這是授權畫的界線。

## 結論

- **資料流是單向五層**：載入器（`LOADM` 分派）→ 播放器（`AMP` 解樂譜）→
  聲道分配器（`CDI` 按聲道範圍分派）→ 混音器（`MCP` 疊成輸出流）→
  輸出驅動（`SDI_*` 寫硬體）。`GUS` 是平行於 `MCP` 的另一條 `CDI` 裝置，
  「無聲」則是第三個裝置（`NOSOUND`）。
- **`CDI` 的註冊單位是聲道範圍**，不是整台裝置：`cdiRegister` 吃一個裝置表加
  起迄聲道號，範例程式用 0 到 31；同一範圍內音樂用低段聲道、
  音效用樂曲聲道數之後的幾段。背景音樂與音效分的就是這一批聲道。
- **`MCP` 的混音主迴圈是單一組語程序**（約 5700 行的 `MCPLAYER.ASM`
  是整個混音器，不是迴圈本身），內部按立體聲旗標、各聲道左右、
  品質旗標、輸出寬度層層分支；
  16 位元與 32 位元兩條路用組譯期條件指令寫在同一份原始碼裡，不是兩份拷貝。
- **`AMP` 的效果器是 24 個同名 `CMD` 程序**（滑音、顫音、琶音、斷音、延音⋯⋯），
  由 `playCommand` 分派；檔案格式辨認集中在 `LOADM` 的 `getType`，
  按魔術數字順序試 FAR、MTM、AMF、S3M、669、STM、MOD（含 TREK／xCHN 變體），
  最後才假設是 15 樂器舊 MOD。
- **自動偵測只有四層**：`initDSMI` 依序試 GUS、PAS、Aria、SB，
  命中後按卡號對應到 `SDI_*` 驅動（SB16 含在 SB 這層裡，用卡型欄位區分）。
  DAC、WSS、PC 喇叭走範例程式的手選單，
  用欄位裡的特殊記號區分（例如 PC 喇叭借 DAC 的卡號、埠記為 `0x42`）。
- 音效引擎（`SFXENG`，Sound effect engine）只有 111 行 C：最多註冊 40 個音效、
  佔用 8 個聲道，五個函式（初始化、註冊、播放、停止、全停）就講完；
  槽滿時按「空槽→同樣本槽→輪替覆寫」偷槽，不回傳失敗。

圖中每一條箭頭都是函式表呼叫。上層只認得下層的表結構，不認得實作檔：
`AMP` 只認得 `CDI`，`MCP` 只認得 `SOUNDDEVICE`，偵測只產出 `SOUNDCARD`。
這種「用結構換解耦」讓新增一張卡只需要寫一支驅動，混音器不用動。

## 1. CDI：聲道是拿來切段出租的

`CDI`（Channel Distributor，聲道分配器）的裝置表 `CDIDEVICE` 在 C 標頭裡是
24 個函式指標，在組語 include 裡是 25 個——組語側多一欄 `getchannelstatus`
（查某聲道是否播放中，音效引擎找空槽就靠它）。欄位涵蓋開關裝置、開關聲道、
設音量、設播放速率（音高）、設左右、播音、停音、暫停、取播放位置⋯⋯
凡是「對某個聲道下命令」的操作都在這張表裡。

關鍵設計是註冊函式吃**聲道範圍**：

```
cdiRegister(裝置表, 起始聲道, 結束聲道)
```

範例程式註冊的是 0 到 31——整台混音器一次租走 32 個聲道。
同一範圍內再分段：背景音樂用低段聲道，音效引擎用樂曲聲道數之後的幾段
（範例程式對音效引擎下的就是「從樂曲聲道數起、要 3 段」），
兩邊走同一張表、互不干擾。音效引擎的初始化函式同樣吃
「起始聲道＋聲道數」，就是為了卡進這批租出去的聲道裡；
它下命令也走 `CDI`（設樂器、播音、設左右、停音都是 `cdi*` 呼叫），
不是繞過分配器直接碰混音器。

封存裡實際定義了三個 `CDIDEVICE` 實例，各自住在自己的組語檔：

| 實例 | 檔案 | 角色 |
|---|---|---|
| `CDI_MCP` | `MCPLAYER.ASM` | 主機軟體混音，再往下接 `SDI_*` |
| `CDI_GUS` | `GUS.ASM` | Gravis UltraSound 卡上發聲，繞過整個 `MCP` 與 `SDI_*` |
| `CDI_NOSOUND` | `NOSOUND.ASM` | 無聲：除時間推進外，所有操作都是空殼 |

`CDI.ASM`（約 590 行）是這張表的 C 語言門面：28 個 `CPROC`
（可同時編出 C 與 Pascal 呼叫慣例的程序巨集——DSMI 同時服務 Pascal 程式，
磁碟輸出驅動就是 Pascal 寫的，見 §4.2）把「對第 N 聲道下命令」
轉成「找到負責第 N 聲道的裝置表、呼叫對應欄位」。
28 個裡 3 個是全域的（初始化、註冊、關閉），25 個按聲道分派，
正好對上組語表 25 欄。
初始化全域、註冊按範圍——因為多個裝置可以各佔一段聲道，
這個不對稱正是「多租戶聲道」的來源。

## 2. MCP：混音器，一個大迴圈加層層分支

`MCP`（Multi Channel Player，多聲道播放器，按原始碼檔頭）是主機端軟體混音：
把租給它的每個聲道上正在播的樣本即時疊加，寫進一塊輸出緩衝，
再由 `SDI_*` 送進音效卡的 DMA（Direct Memory Access，
音效卡不經 CPU 直接從記憶體抓資料的機制）。

### 2.1 主迴圈按旗標分支，不按卡分支

混音主迴圈 `mixBuffer` 是單一組語程序，逐聲道推進，每個聲道按旗標層層分支：
先看卡的立體聲旗標，再看各聲道的左右（pan）設定，
後面還有品質旗標與輸出寬度（8／16 位元）的分支。
重點：分支條件全是模式旗標，沒有一條看目標卡型號——
迴圈只寫記憶體裡的緩衝，「緩衝怎麼進硬體」是 `SDI_*` 的事。
這就是為什麼新增一張卡只需要寫一支 `SDI_*`，混音器一行都不用動。

### 2.2 16 位元與 32 位元是同一份原始碼

同一個迴圈要同時服務 16 位元 DOS 程式與 32 位元 DOS 延伸器程式
（DOS 延伸器是讓 DOS 程式跑在 32 位元保護模式的載入器）。
做法不是寫兩份，而是在關鍵處用字面就叫 `IF16`／`IF32` 的組譯期條件巨集
內嵌兩種寫法：

- 16 位元路：樣本指標是區段（segment）加位移，取樣本前要正規化區段；
- 32 位元路：樣本指標是平坦 32 位元（不分段的線性位址），直接取用。

條件只出現在「算出下一個樣本位址」這種地方，混音數學本身兩條路共用。
辨認特徵：同一個迴圈裡出現成對的「區段正規化 vs 直接定址」，
就是這套手法的結構指紋。

### 2.3 查表法：音量表與品質表

即時混音的乘法相對查表太慢（每個聲道每個取樣點都要乘一次音量係數），
`MCP` 把音量換算預先算好存在表裡：

- 兩張音量曲線：線性表與立體聲表各 32 階；立體聲模式選用立體聲那條曲線，
  左右聲道的區分在 `mixBuffer` 的 pan 分支處理，不在表裡；
- 品質模式分兩階段查表合併（第一階段逐聲道混成中介緩衝，第二階段合併輸出），
  表大小由 `QUALITYSIZE`（8 位元）與 `QUALITYSIZE16`（16 位元）兩個常數決定；
- 混音工作表 `MCP_TABLESIZE` 是 `(32*256*2+32)`：音量範圍 0–64 對半拆成
  32 段（正好對上 32 階曲線）× 256 個樣本值 × 2 位元組；
  尾巴的 `+32` 在原始碼裡沒有註解，用途未知。

數字會說話：`(32*256*2+32)` 這種形狀——階數 × 256 × 樣本寬度——
是「把乘法燒成表」的標準長相，在別家函式庫看到同形狀的常數可以直接聯想。

### 2.4 MCP 的對外 API

`MCP` 對上層（`CDI` 與應用程式）開的介面大致分三群：

- 生命週期：`mcpInitSoundDevice`（先掛 `SDI_*` 表）→ `mcpInit`（再起混音器）→
  `mcpClose`；順序不能反，因為 `mcpInit` 要把混音器緩衝的位置交給驅動
  （經 `SDI` 的 `initOutput` 欄）。上層的 `CDI` 反而比 `MCP` 晚初始化——
  下層是上層的資源，先備妥下層是自然的順序。
- 播放控制：`mcpPoll`（吃時間推進混音時鐘）、`mcpSetupChannels`（配聲道與音量表）、
  啟動／停止／暫停聲部。這裡的聲部指 voice（`mcpStartVoice` 一族的操作單位），
  與模組的軌、CDI 的聲道是不同層的詞，不要混用。
- 查詢：`mcpGetDelta`（取時間差）、`mcpGetCardInfo`（回傳卡資訊）。

內部的 `firstChannel1`／`firstChannel2` 不是聲道起點，
而是每個混音遍歷（pass）歸零一次的計數器，在 pan 分支裡累加，
用於立體聲清緩衝的判斷——和 CDI 的聲道範圍無關。

## 3. AMP：播放器，24 個效果器程序

`AMP`（Advanced Module Player，進階模組播放器，按原始碼檔頭）負責讀樂譜。
樂譜是二維格子：直行是軌（track，同一時刻並行的發聲線），橫列是時間先後；
tick 是播放器推進樂曲的時間單位（原始碼以 `moduleinfo.ticks` 計數）。
每個 tick 看當前列有哪些音符與效果指令，換算成「第 N 聲道、
用某樣本、以某播放速率（音高）、某音量播」的命令，丟給 `CDI`。

效果器是這層的主體：`AMPLAYER.ASM`（約 2800 行）裡有 24 個
`CMD` 開頭的程序，由 `playCommand` 按指令碼分派：

| 類別 | 程序（概念名） | 作用 |
|---|---|---|
| 音高 | 滑音、滑向目標音、超精細滑音、琶音 | 改變聲道播放速率 |
| 顫動 | 顫音、震音、音量顫動、滑音加音量 | 週期性調制音高或音量 |
| 包絡 | 設音量、絕對音量、精細音量、斷音、延音、重觸發 | 音量與發聲長度 |
| 定位 | 跳段、斷行、取樣偏移、同步記號 | 樂曲流程控制 |
| 音色 | 設樂器、設左右、精細調音、設速度 | 聲道屬性 |

`playNote`（起音）與 `playTrack`（推進一軌）是另外兩個非 `CMD` 程序：
起音負責把「音符＋樂器」換算成樣本與播放速率，推進負責走格子。
注意新舊版差異：作者留下的 FC 檔案比較輸出（`*.NEW`，
新舊版並排的差異檔）顯示，`cmdDelayNote`（延音）在新版改名為 `cmdNoteDelay`，
讀不同年份的封存要對一下名字。

`AMP.H` 開了 8 個載入入口：一個通用（`ampLoadModule`，先辨認格式再分派）
加 7 個指定格式（MOD、STM、AMF、S3M、669、MTM、FAR）。
辨認邏輯見第 6 節。

## 4. SDI：輸出驅動，一張 12 針的插頭

`SDI`（Sound Device Interface，聲音裝置介面）是 `MCP` 與硬體之間的轉接層。
介面結構 `SOUNDDEVICE` 是 12 個函式指標，剛好是「輸出裝置的一生」
（「針」是借用硬體接腳的比喻，下文統一稱欄位）：

```
開啟裝置 → 開啟輸出 → 設取樣率 → 啟動輸出 ⇄ 暫停／繼續 → 停止輸出 → 關閉輸出 → 關閉裝置
        ＋ 取緩衝位置 ＋ 喇叭開／關
```

流程圖裡的「暫停／繼續」與「喇叭開／關」各佔兩欄（暫停、繼續、開、關各一），
8＋2＋2 正好 12 欄。

應用程式永遠不直接碰 `SDI_*`：`initDSMI` 按偵測到的卡號
把對應的 `SDI_*` 表交給 `mcpInitSoundDevice`，之後 `MCP` 只認這張表。

### 4.1 卡資訊結構

偵測的產物是 `SOUNDCARD`：卡號、版本、32 字元名稱、I/O 埠（x86 port I/O 位址）、
IRQ（中斷線號）、DMA 通道、最低／最高取樣率（Hz）、立體聲旗標、
混音器旗標、樣本寬度、8 位元組保留欄。
卡號 1 到 10 在 `MCP.H` 寫死，全稱按範例選單與版本字串還原：

1 Sound Blaster、2 Sound Blaster Pro、3 Pro Audio Spectrum、
4 Pro Audio Spectrum+、5 Pro Audio Spectrum 16、6 Sound Blaster 16、
7 DAC（並列埠接數位類比轉換器的外接盒）、8 Aria、9 Windows Sound System、
10 Gravis UltraSound。

### 4.2 各驅動一覽

六支組語驅動的版權字串都署名 Otto Chrons，年份橫跨 1992 到 1994，
且六支的字串尾巴都帶 `,0,1Ah`（是共通格式，不是某支的特徵）：

| 驅動 | 約行數 | 版本字串自述 |
|---|---|---|
| `SDI_SB`（含 SB Pro 雙入口） | 約 1000 | SB & SB Pro v2.0（1992、1994） |
| `SDI_ARIA` | 約 950 | Aria v1.0（1993） |
| `SDI_DAC` | 約 760 | DACs v1.5（1992、1993） |
| `SDI_SB16` | 約 700 | SB16 v2.0（1993、1994） |
| `SDI_PAS` | 約 700 | PAS, PAS+ and PAS 16 v2.0（1993、1994） |
| `SDI_WSS` | 約 690 | WSS v1.0（1993） |
| 磁碟輸出 | 約 160（Pascal） | 把混音結果寫檔，不出聲 |

幾處值得記的結構特徵：

- `SDI_SB` 為 SB Pro 另設一組入口（雙 `SOUNDDEVICE` 實例），
  因為 SB Pro 的立體聲埠協定與舊 SB 不同。
- `SDI_DAC` 的裝置自述名就是 "Simple DAC"；並列埠 DAC 靠使用者手選
  （見第 5 節）。字串尾的 `0x1A` 與 STM 簽名 `0x021A` 的低位元組數字相同，
  純屬巧合，兩處脈絡無關。
- `SDI_PAS` 初始化時檢查 `MVSOUND.SYS` 是否存在（驗其 `MV` 簽名）——
  那是 PAS 卡的 DOS 常駐驅動，DSMI 只驗收它先配好硬體，不代勞。
- 沒有 `SDI_MV`：封存裡有 Media Vision 卡的偵測檔（`DETECTMV`，
  Media Vision 是 PAS 的製造商），但沒有對應的輸出驅動，
  `initDSMI` 也從不呼叫它。只能說到這裡——是棄置、待完工還是另有他用，
  原始碼沒有解釋。
- 磁碟輸出驅動是 Pascal 寫的（約 160 行），佐證 `SOUNDDEVICE`
  這張表的呼叫慣例相容：C 寫的混音器照連不誤。

## 5. 偵測與初始化：自動只走四層

### 5.1 `initDSMI`：偵測、選驅動、起混音

`INITDSMI.C` 的 `initDSMI` 是應用程式真正的總入口，
做完四件事：偵測 → 選 `SDI_*` → 起計時服務 → 起混音器。
自動偵測的順序寫死，只有四層：

```
detectGUS → detectPAS → detectAria → detectSB
```

命中任一層就停，再按卡號對應驅動（SB／SB Pro／PAS 家族／SB16／Aria），
GUS 命中則跳過 `MCP` 與 `SDI_*`（走 `CDI_GUS` 直通道）。
DAC、WSS、PC 喇叭不在自動鏈裡，只能請使用者手選。
為何 WSS（正規音效卡）不在鏈內，原始碼沒有解釋，此處只能記為未知。

### 5.2 兩套 SB 偵測：新舊並存

SB 的偵測新舊兩份同名互斥（都定義 `detectSB`，只能連其一），
加上兩個底層硬體探測檔，共四個檔案：

- `DETSB.C`（1994，C 寫）：先讀 `BLASTER` 環境變數，有就直接解析
  （預設埠 `0x220`、IRQ 7、DMA 1；認 `A` 位址／`I` IRQ／`H` 高位 DMA／
  `D` DMA／`T` 卡型五個欄位；卡型 1 是舊 SB、2／4／5 是 SB Pro、
  3 是版本 2.0、其他值一律當 SB16）。SB16 就含在 SB 這層裡，
  不是自動鏈的第五層。沒有 `BLASTER` 才做硬體探測。
- `DETECTSB.ASM`（約 1200 行，組語）：另一套純硬體探測，
  對 SB、SB Pro、SB16 各有一套探測程序。

C 版呼叫的底層硬體探測分兩檔：`detectSBHW` 與 `detectSBProHW`
住在 `DETSBHW.ASM`（約 780 行），`detectSB16HW`
住在 `DETSB16H.ASM`。讀到 `detectSB` 要先問是哪一檔的，
它們的簽名與行為都不同。

### 5.3 GUS 與手選單

`DETGUS.C` 只認 `ULTRASND` 環境變數，不做硬體探測；
變數格式是五個逗號分隔值（埠、DMA、第二 DMA、IRQ、第二 IRQ），
回填的取樣率範圍是 19293 到 44100 Hz。19293 不是漂亮的 20000——
數值本身可做辨認線索，但它對應到卡上哪個時鐘，原始碼沒有解釋。

範例程式（`EXAMPLE.C`）的手選單列了 13 個選項：
9 張卡（SB、SB Pro、SB16、PAS、PAS+、PAS16、Aria、WSS、GUS）
加 3 種 DAC 變體加 PC 喇叭。後四個共用卡號 7（`ID_DAC`），
用欄位裡的特殊記號區分：

- 單聲道 DAC（並列埠，預設埠 `0x378`）：無特殊記號；
- 立體聲雙 DAC：`dmaChannel` 記為 1（借用欄位當記號，不是真的 DMA）；
- 單埠立體聲 DAC：`dmaChannel` 記為 2；
- PC 喇叭：卡號同借 7，I/O 埠記為 `0x42`。

這是「結構不夠用就拿欄位當暗號」的典型 DOS 手法：
`SOUNDCARD` 沒有「子型號」欄，作者就借用 DMA 與埠欄位傳暗號。
`SDI_DAC` 認得這些暗號：看到埠是 `0x42` 就走喇叭路
（`0x42` 是 PC 計時器通道 2 的埠，通道 2 接 PC 喇叭——這是 PC 架構常識，
不是 DSMI 原始碼寫的）。並列埠 DAC 則是外接盒吃並列埠的資料腳位出聲，
無聲卡的機器外接一個小盒子就能播模組音樂。

## 6. 載入器：格式辨認是一串魔術數字

`LOADM.C`（約 220 行）的 `getType` 是所有格式的總開關：
讀檔頭幾個位元組，按固定順序比對，命中就把後續交給對應載入器。
順序本身就是知識——排前面的格式有優先權：

```
FAR → MTM → AMF → S3M → 669 → STM → MOD → (TREK / xCHN) → 假設為 15 樂器 MOD
```

比對位置各不相同，正好反映各格式把簽名放哪：

| 格式 | 簽名位置 | 簽名長相 |
|---|---|---|
| FAR | 檔頭 | `0xFE524146`（`FAR` 三字加第 4 位元組 `0xFE`） |
| MTM | 檔頭 | 檔頭 `MTM` 記號（遮罩比對，只比低 3 位元組） |
| AMF | 檔頭 | `AMF` 三字加版本位元組（遮罩比對，蓋掉版本差異；4 聲道舊版另有兩種版本值） |
| S3M | 位移 `0x2C` | `SCRM` |
| 669 | 檔頭 | `0x6669`（ASCII `if` 兩字，Composer 669 的簽名頭） |
| STM | 位移 28 | 版本字比對值 `0x021A` |
| MOD | 位移 1080 | `M.K.`、`M!K!`、`FLT4` 任一 |
| TREK / xCHN | 位移 1080 | `FLT8`（StarTrekker 8 軌，按載入器註解）或 FastTracker 簽名（一位數 `xCHN` 另有遮罩；10–32 軌另有一組遮罩，聲道數取自低兩位元組，最多鉗到 32） |

都沒中就假設是 15 樂器舊 MOD（`MOD_15`，沒有簽名欄的上古格式），
聲道數填 4——認不出的退路就是當最老的格式試。

七種具名格式（MOD、STM、AMF、S3M、669、MTM、FAR）各有專屬載入器，
TREK、xCHN、`MOD_15` 都歸 `loadMOD` 處理，是 MOD 的變體而非獨立格式。
各載入器行數：S3M 約 620、MOD 約 600、MTM 約 500、STM 約 450、
FAR 約 450、669 約 400、AMF 約 260。另有一份 `OCTLOAD.C`（約 440 行，
檔頭自述 Octalyzer loader），它與 `MODLOAD.C` 定義的是同一個 `loadMOD` 入口——
兩份只能連其一；誰新誰舊原始碼沒有明說，此處不下斷言。
值得記的三處：

- MOD 載入器按 `MOD_15` 還是 MOD 決定讀 15 或 31 個樂器，
  播放速率換算用微調值（finetune，4 位元、16 段）查表。
- 各直接載入入口（`ampLoadXXX`）自帶前置簽名守衛，
  因為它們繞過 `getType`：S3M 入口驗 `SCRM`，MOD 入口驗 1080 位移的簽名。
  S3M 的樂器基準速率來自 `c2spd`（C-2 音高的取樣率）欄位：
  S3M 的音高是相對值，不是絕對頻率。
- AMF 的 C 版（`AMFLOAD.C`）才是 `LOADM` 用的；
  `AMFLOAD.ASM` 是給 Pascal 的移植（`model tpascal`，
  匯出 `loadAMFasm`，全封存只有 `EXAMPLE4.PAS` 用它）。

## 7. 完整啟動序列

把 `initDSMI` 與範例程式的流程壓成一份虛擬碼（只保留呼叫順序，
與原文的敘述、命名順序無關）：

```
偵測卡（GUS → PAS → Aria → SB，自動鏈）
依卡號選輸出驅動表（GUS 除外：走卡上直通道）
掛驅動表給混音器
啟動計時服務（設 8253 速率）
啟動混音器（混音器把緩衝位置交給驅動）
初始化聲道分配器
註冊聲道範圍（例如 0–31 租給混音器）
初始化播放器（ampInit）
載入模組（通用入口先辨認格式；直接入口自帶簽名守衛）
播放（可選循環）／停止
依反序關閉：播放器 → 混音器 → 驅動（cdiClose 存在，但兩份範例都沒呼叫它）
```

時鐘鏈：計時服務設好 8253 之後，`mcpPoll` 每輪吃時間推進混音，
`mcpGetDelta` 取本輪時間差；沒有音效卡時，`NOSOUND` 用 BIOS 滴答換算出
虛擬時間（見 §8），同一套呼叫照走。

音效走另一條小路：初始化音效引擎（指定它租哪段聲道）→
註冊樣本（最多 40 個）→ 按把手（handle，註冊回傳的編號）播放
（指定音量、播放速率、左右）→ 停止／全停。
背景音樂播到一半插進一個爆炸音，就是 `PlaySFX` 經 `CDI` 下命令的事，
`AMP` 完全不知情——分層的意義正在這裡。

## 8. 邊角：SFX 與 NOSOUND

`SFXENG.C`（111 行）是全函式庫最薄的一層：靜態陣列記 40 個已註冊音效，
8 個播放槽。槽滿不回傳失敗，而是偷槽：先找沒播的空槽，
沒有就找播同樣本的槽，再沒有就輪替覆寫；只有把手非法才回傳 -1。
五個函式講完：初始化（吃起始聲道與聲道數）、註冊（吃樣本描述）、
播放（吃把手、音量、播放速率、左右）、停止、全停——
播放與停止都是 `cdi*` 呼叫，經分配器下命令。

`NOSOUND.ASM`（約 140 行）是「沒音效卡時讓遊戲照跑」的關鍵：
除時間推進外，所有 `CDIDEVICE` 欄位都是空殼。
時間推進讀 BIOS 時鐘滴答（`40h:6Ch`）換算成微秒，
`getDelta` 每輪回傳可用微秒數，上限 `TIME_DELTA = 100000`（0.1 秒）。
有了它，沒卡的機器跑的是同一套呼叫，差別只是靜音。

## 給 remake 與逆向的辨認線索

只列原始碼層級的結構特徵（授權禁止逆向本套件，不做位元組簽章）：

- 函式表形狀：`CDI` 裝置表（C 標頭 24 欄、組語 25 欄），
  `SDI` 驅動表 12 欄。看到「大表包小表、GUS 繞過小表」的連接方式，
  就是 DSMI 的架構。
- 常數形狀：`(32*256*2+32)` 類的「階數 × 256 × 寬度」是混音查表；
  `19293` 是 GUS 取樣率下限；`0x42` 埠配 DAC 卡號是 PC 喇叭暗號。
- 字串：各 `SDI_*` 的版本自述（`SDI for <卡> vX.Y - (C) 年份 Otto Chrons`）、
  `Simple DAC`、`BLASTER`／`ULTRASND` 環境變數名、`SCRM`。
- 流程：`BLASTER` 解析（認 `A`／`I`／`H`／`D`／`T`）先於硬體探測；
  格式辨認順序 FAR→MTM→AMF→S3M→669→STM→MOD（含 TREK／xCHN）→退路。
- 工具鏈痕跡：封存裡附帶的目的檔是 Turbo Assembler 3.1 編出的
  OMF（Object Module Format，目的檔格式），裡面嵌著來源檔名
  （`GUS.ASM`、`MODEL.INC`、`MCP.INC`、`GUS.INC` 字串直接可見）——
  在同時期的遊戲執行檔裡看到同組檔名殘留，可列入考慮。
