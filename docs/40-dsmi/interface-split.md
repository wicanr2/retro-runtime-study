# DSMI：一份組語核心，三種語言接得上

## 結論

DSMI（Digital Sound and Music Interface，Otto Chrons 與 Jussi Lahdenniemi 在 1990 年代初寫的
DOS 音效與模組音樂函式庫）常被說成「有 C、組語、Pascal 三套介面」。讀過原始碼之後，比較準確的說法是：

- **核心是一份組語原始碼，用組譯期符號切換呼叫慣例，編出 C 版與 Pascal 版兩套目的碼。**
  建置檔裡看得很清楚：Pascal 那條路組譯時定義兩個符號、再用 Pascal 編譯器編 unit；C 那條路不帶那些符號。
  所以不是「同一份目的碼給三種語言連」，是**同一份原始碼、兩套產物**。
- **外圈則是各語言各有一份實作。** 模組載入器、記憶體管理、膠水層在 C 與 Pascal 各寫一次。
  原始碼自己用檔頭措辭區分了這兩類：介面翻譯的寫「譯自 C 標頭」，完整移植的寫「原始的 C 版本由⋯⋯」。
- **`CDI` 在架構的中央，不在 `MCP` 底下。** `CDI`（Channel Distributor）定義一張裝置函式表，
  而 `MCP`（主機軟體混音）、`GUS`（卡上發聲）、「無聲」各自是註冊進去的一個裝置。
  `SDI_*` 那一層只掛在 `MCP` 底下。
- **Gravis UltraSound 不是「裝置介面層的例外」，它是 `CDI` 的另一個裝置**——走的路和 `MCP` 平行，
  整個 `MCP` 與 `SDI_*` 都被繞過。
- 封存裡有不少東西**不是原始碼**：兩封 1994 年的電子郵件、十一份檔案比較指令的輸出、
  一個組語編出的目的檔、第三方廠商的 include、Borland 的 Turbo Pascal 單元。

這一篇只讀原始碼。**DSMI 的授權禁止逆向該套件**（授權全文就在封存的 `LICENSE.DSM`），
所以沒有反組譯、沒有位元組簽章，也沒有編譯或實跑。

## 根本問題

### 1992 年的 DOS 沒有音訊 API

作業系統不管聲音。要出聲就得自己認卡、自己設好 DMA（Direct Memory Access，讓音效卡不經 CPU
直接從記憶體讀音訊資料的機制）、自己餵資料。而市面上的卡彼此不相容：
Sound Blaster 系列、Pro Audio Spectrum、Windows Sound System、Gravis UltraSound，
還有一堆相容品。每張卡的偵測方式、埠位址、資料格式、中斷行為都不一樣。

### 模組音樂要在執行時自己混音

一個模組（module）檔案裡同時裝著兩樣東西：**樣本**（sample，每種音色的一小段錄音）與**樂譜**
（哪一軌、在哪一刻、用哪個樣本、彈什麼音高、加什麼效果）。播放時沒有現成的音源可以叫，
程式得自己把同時發聲的好幾軌樣本**即時疊加**成一條輸出音訊——這件事就是**混音**。

能同時疊幾軌有上限，那個上限就是**聲道**數（這裡指可同時發聲的軌數，不是立體聲的左右聲道）。
遊戲通常要一邊放多軌的背景音樂、一邊隨時插進音效，兩邊分的是同一批聲道。

格式也一樣亂：追蹤器（tracker，編輯這種音樂的程式）音樂從 Amiga 的 MOD 開始，
PC 上冒出 STM、S3M、669、MTM、FAR、ULT、OCT⋯⋯每種的樣本編碼、效果指令、聲道數都不同。

### 寫遊戲的人用什麼語言都有

1992 年的 DOS 遊戲圈，C、Turbo Pascal、純組語都是主流。函式庫作者如果每種語言各寫一份實作，
維護成本會乘以三，而且三份的行為遲早會不一致。

### 一份原始碼，兩套目的碼

建置檔有兩條路。Pascal 那條在組譯核心的 `.ASM` 時定義兩個符號（一個表示「給 Pascal 用」、
一個是 Pascal 的呼叫慣例開關），再用 Pascal 編譯器編各個 unit；C 那條用 C 編譯器配一份設定檔，
組譯時不帶那些符號。組語原始碼裡對應的是 `IFDEF` 分支與 model 指令。

所以「三種語言共用」共用的是**原始碼**，不是同一個目的檔。Pascal 的 unit 用連結指令把
對應的目的檔拉進來（`MCPlayer.OBJ`、`cdi.obj`、`gus.obj`、`SDI_SB.OBJ`⋯⋯），
**那些目的檔一律對應樹裡的 `.ASM`，沒有一個對應 `.C`**——這是「共用的是組語核心」最直接的證據。

代價也看得到：Pascal 那邊得自備一層 C 支援函式（幾乎每支 Pascal 載入器都會用到），
因為組語核心是照 C 的習慣寫的。

### 兩類 Pascal 檔，檔頭自己標了

| 類型 | 檔頭怎麼寫 | 實作段長什麼樣 | 例子 |
|---|---|---|---|
| 介面翻譯 | 「⋯⋯的 unit 標頭檔；原始的 C **標頭**由 Otto Chrons 撰寫」 | 一個連結指令加一串外部宣告 | `MCP`、`AMP`、`CDI`、`GUS`、各 `SDI_*`、`TIMESERV`、`MIXER`、`VDS` |
| 完整移植 | 「原始的 C **版本**由⋯⋯」，沒有連結指令 | 真的 Pascal 實作，幾百行 | 各模組載入器、GUS 的記憶體管理、音效引擎 |
| Pascal 獨有 | 只有 Pascal 版 | 同上 | UltraTracker 的載入器、把音訊寫到磁碟的那個裝置 |

**讀封存時用檔頭這一句話判斷最省事**：寫「header」的是翻譯，寫「version」的是另一份實作。

C 標頭與 Pascal unit 的長度常差一倍，除了 record 比 struct 囉嗦，更主要的原因是
**同一個函式要宣告兩次**：介面段一次、實作段的外部宣告再一次。

### 分層：`CDI` 在中央

`CDI` 定義一張二十幾個函式指標的裝置表，並提供「把這個裝置註冊到第幾號到第幾號聲道」的呼叫。
`MCP` 與 `GUS` 各自對外宣告一個這樣的裝置，「無聲」也有一個。初始化時依偵測結果挑一個註冊進去。

| 層 | 模組 | 做什麼 |
|---|---|---|
| 載入器 | `MODLOAD`、`S3MLOAD`、`STMLOAD`、`669LOAD`、`MTMLOAD`、`FARLOAD`、`AMFLOAD` | 把各種模組格式讀成記憶體裡統一的模組結構 |
| 音樂與音效 | `AMP`（Advanced Module Player）、`SFXENG` | 前者播模組音樂，後者管音效；**各自佔一段聲道範圍** |
| 聲道裝置抽象 | `CDI`（Channel Distributor） | 一張裝置函式表加註冊機制；上層只呼叫這一組 |
| 裝置實作 | `MCP`（Multi Channel Player）／`GUS`／無聲 | `MCP` 在主機上把多軌樣本混成一條音訊流；`GUS` 把樣本上傳到卡、由卡發聲 |
| 輸出後端 | `SDI_*`（Sound Device Interface） | **只掛在 `MCP` 底下**：SB、SB16、Pro Audio Spectrum、Windows Sound System、DAC、ARIA，另有一個寫到磁碟的 |
| 旁掛的服務 | `DET*`（偵測，啟動時跑一次）、`TIMESERV`（計時）、`MIXER`（音效卡**硬體混音器**的音量控制，與 `MCP` 做的取樣疊加是兩回事）、`VDS`（虛擬 DMA 服務）、各種樣本記憶體管理 | 不在播放資料的主鏈上 |

音效與音樂的分工不是靠誰去仲裁，而是**切聲道範圍**：註冊裝置時給定區間，音效引擎初始化時也給定
「從第幾號聲道起、要幾個」。兩邊各拿一段，互不重疊。

`SDI_*` 裡那個「寫到磁碟」的版本特別能說明這個介面切得夠乾淨：它不是給使用者的功能，是除錯管道，
把本來要送給音效卡的資料寫成檔案——而且**它是用 Pascal 寫的，沒有 C 或組語版本**，
等於是不碰組語核心的人照著那張函式表另外接上去的一個裝置。

### 載入器與離線轉檔工具是同一份原始碼

每種模組格式一支載入器，載入時就把檔案讀成記憶體裡統一的模組結構，播放核心只認那個結構。
**支援一種新格式的成本是「寫一支載入器」，不是「改播放核心」。**

封存裡另有一組轉換器原始碼：它們不是獨立的程式，而是**先定義一個開關、再把同一支載入器的原始碼整份引入**，
編出「離線轉檔」的版本。那支離線工具把模組另存成 DSMI 自己的 AMF（Advanced Module Format）檔。
一份載入器原始碼，換一組編譯開關就是兩種產物。

**注意：樹裡有原始碼不等於功能接上。** 格式派送器實際認得的是 MOD（含兩個變體）、STM、S3M、669、MTM、FAR、AMF
這七種；UltraTracker 與 Oktalyzer 的載入器樹裡有，但沒有接進派送器，模組型別的列舉裡也沒有它們。

### GUS 為什麼走另一條路

其他卡的模型是「主機把所有聲道混成一條音訊流，再餵給卡」——那就是 `MCP` 加 `SDI_*` 做的事。
GUS 不是：它自己有音訊記憶體，樣本先上傳到卡上，播放時由卡自己混音。

所以 GUS 沒有 `SDI_*` 模組，它**直接是 `CDI` 的另一個裝置**，與 `MCP` 平行。
初始化時如果偵測到 GUS，註冊的就是它，整個 `MCP` 與 `SDI_*` 都不參與。

它需要的額外東西是**卡上記憶體的配置管理**：樣本放在卡上，主機不能直接定址，
所以配置器回傳的是代號（handle）而不是指標。有趣的是這不是 GUS 專屬的形狀——
把樣本放進 EMS（那個年代的擴充記憶體）時也是同一個問題、同一種解法。
**兩者是同一個抽象的兩個後端**：記憶體不在直接定址範圍內，就用代號取代指標。
樣本放 EMS 還是一般記憶體，是**編譯期**選的。

## 讀這份封存的人要知道的事

| 你看到的 | 意思 |
|---|---|
| `.H`／`.PAS`／`.INC` 同名三份 | 同一個模組的三種語言介面；`.PAS` 是不是只有宣告，看檔頭寫「header」還是「version」 |
| 某模組只有介面檔，沒有同名的 `.C`／`.ASM` | **不代表沒有實作**，去找名字不同的實作檔：`MCP` → `MCPLAYER.ASM`、`AMP` → `AMPLAYER.ASM` |
| Pascal 檔名比 C 短或多一個底線 | Pascal 的檔名與 unit 名有長度與首字元限制：`SDI_SB16.H` 的 Pascal 版叫 `SDI__SB1.PAS`，`669LOAD` 的叫 `_669LOAD.PAS`（識別字不能以數字開頭）。grep 封存時最容易漏的就是這一類 |
| `.CH` 與 `.NEW` 檔 | 不是原始碼，是 DOS 檔案比較指令的輸出——作者在兩份拷貝或新舊版本之間做的差異比對殘留 |
| `GUSMIX.PAS`、`S3MLOAD.JIM` | **不是模組**，是 1994 年第三方寄給作者的電子郵件（附了提問者自己寫的程式片段） |
| `.OBP` 檔 | 組語編出來的目的檔。授權禁止逆向，別碰 |
| `BINARY.INC`、`COMMON.INC`、`MASM.INC` 這類 | 第三方廠商（Pro Audio Spectrum 原廠）的 include，不是 DSMI 的碼 |
| `CRT.ASM`／`CRT.PAS` | Borland 的 Turbo Pascal 單元，也不是 DSMI 的碼 |
| `PMP*`、`GMP*` 一批 Pascal 檔 | 以 DSMI 為基礎寫的播放器程式（Protected／Graphical Module Player），不是函式庫本身 |
| `DMP*` | 同樣是播放器（Dual Module Player），但它是**C 寫的** |
| `.DOC`、`.REV`、`LICENSE.DSM` | 手冊、版本紀錄與授權全文 |
| 檔頭年份 | DSMI 自己的碼集中在 1992–1994；另有 1988 與 1991 的第三方檔混在裡面 |

## 給 remake 讀者的指路

這一篇只做到架構層級，但下面幾處是「要對行為就得看」的地方，都在標頭裡：

- **支援哪些模組格式**：模組型別的列舉（七種，見上）。
- **效果指令的完整集合**：模組播放器標頭裡的指令列舉。
- **聲道上限與分配**：裝置註冊與音效引擎初始化都收「起始聲道、數量」，設計上限是 32 聲道。
- **音效卡的參數結構**：埠位址、DMA 通道與中斷、取樣率上下限、單雙聲道、樣本位元數，
  以及雙緩衝的實體位址與大小——這組欄位就是「當年怎麼設 DMA 雙緩衝」的完整答案。
- **卡片編號常數**：每張卡一個號碼，在設定檔或執行檔裡看到那些數字就能認出 DSMI。
- **品質開關**：混音核心有幾個開關（音質、486 專用路徑、單聲道），不同組合走不同的混音路徑。
- **後製效果**：混音核心留了一個效果函式的掛勾，樹裡有殘響與濾波兩支實作。
