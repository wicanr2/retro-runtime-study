# 目標

這個知識庫要讓做老遊戲 remake 或逆向的人，拿到一支 1990 年代初用 Borland C++ 2.0 編譯的 DOS 程式時，
能做到三件事：認出哪些函式是編譯器與函式庫帶進來的、知道那些函式的確切行為、
把心力留給遊戲自己的邏輯。Borland 做完之後，再用同樣的方法處理 Microsoft Visual C++ 1.0／2.0 的 CRT
與兩套 DOS 音效函式庫 DMX、DSMI；另外沿著 Watcom C 的版本演進（1988–1993），整理 16 位元到 32 位元 DOS extender 的工具鏈。

每一條結論都要有證據，最好的證據是**對拍**（oracle）：用原廠編譯器把原廠函式庫原始碼重編一次，
逐個目的檔和原廠出貨的 `.LIB` 比對。重編結果和出貨版相同，就證明「讀這份原始碼得到的結論，
適用於真實執行檔裡的那份程式碼」。

## 四個階段

| 階段 | 要回答的問題 | 公開產出 | 文件 |
|---|---|---|---|
| M1 Borland runtime 分析 | 原始碼能不能代表出貨的函式庫？同一份原始碼怎麼變成五個記憶體模型？編譯器替程式偷偷呼叫了哪些函式？程式怎麼啟動、怎麼結束？遊戲真正呼叫的檔案 I/O、`printf`、heap、conio 行為是什麼？ | 第一批三篇文章；第二批四篇主題文章與範例程式 | [M1](M1-borland-runtime.md) |
| M2 BCC 反組譯 | BCC 2.0 編出的程式碼在反組譯裡長什麼樣？怎麼自動認出函式庫函式？ | 一篇產生碼特徵、一篇廠牌與模型判斷、位元組簽章與產生工具、文章索引 | [M2](M2-bcc-disassembly.md) |
| M3 其他函式庫 | VC++ 1.0 的函式庫怎麼切份？DMX 各版改了什麼？DSMI 的三套介面怎麼分工？ | 三篇文章（切份、DMX 版本差異、DSMI 介面分工）；**沒有對拍，結論最高到「已證實（原文）」** | [M3](M3-other-libraries.md) |
| M4 Watcom：從 16 位元到 DOS extender | Watcom C 6.5（1988）與 C/386 7.0（1989）怎麼產生碼、依附哪種 extender？到 9.x 的 DOS/4GW、DPMI、LE 格式改了什麼？ | 分批：第一批是素材取得與盤點加一篇 6.5 的 runtime 文章；後續批次才做 32 位元、extender 與版本演進 | [M4](M4-watcom.md) |

記憶體模型（memory model）是 16 位元程式選擇函式呼叫與資料指標要用 2 bytes 還是 4 bytes 的組合，
small／compact／medium／large／huge 五種各需要一份函式庫，說明見
[總覽文章](../00-overview/era-and-libraries.md)。

## 順序與依賴

M1 → M2 → M3，階段內大致照「對拍 → 研究筆記 → 公開文章」的順序。M4 不依賴 M2、M3，可以獨立排程；
但 M4 沒有原廠函式庫的原始碼，流程換成「取得與盤點 → 反組譯與實測 → 研究筆記 → 公開文章」，
結論最高到「已證實（實測）」，不會有對拍。
M1 的第二批（函式庫主題文章）排在 M2 之後：它的「在執行檔裡怎麼認」直接用 M2 產生的簽章與產生碼特徵。

- **M1 在 M2 之前**：M2 的位元組簽章要從「已證明和出貨版相同」的目的碼產生；沒有 M1 的對拍，
  簽章認出來的只是「自己編的版本」，不保證等於遊戲裡連結進去的版本。
- **研究在文章之前**：文章不能放原始碼（授權禁止），只能寫機制與行為規格；機制要先在不公開的研究筆記裡讀清楚、
  對拍確認，才改寫成文章。
- **M3 會回頭補 M1、M2**：R4 啟動與結束鏈的 Microsoft 對照、判斷廠牌的文章裡 VC++ 1.0 的部分，
  都要等 M3 取得 VC++ 1.0 工具鏈。在那之前，這些段落在文章裡列為未知，不因此擋住 M1、M2 結案。

## 追蹤方式

| 查什麼 | 去哪裡 |
|---|---|
| 公開產出（文章、簽章、索引）的狀態 | 本 repo 的 [issues](https://github.com/wicanr2/retro-runtime-study/issues)，依 milestone 分組 |
| 本 repo 未完成項的機器檢查 | `worklist.json`，跑 `tools/worklist.py`；每條的 `issue` 欄位對到上面的 issue |
| 研究項目（對拍、研究筆記、反組譯） | 在不公開的研究工作區追蹤；本目錄的文件以 worklist id（例如 `oracle-bcpp20-cwin`）標示 |

本目錄只寫目標、完成條件與依賴，不記進度；某一項做完沒有，以 issue 狀態與 `tools/worklist.py` 的輸出為準。

## 邊界

- **不放原文。** Borland、Microsoft、DMX、DSMI 四份來源的授權都禁止散布原始碼；M4 的 Watcom 出貨檔同樣不放；open-watcom-v2 可以引用必要的短片段，每段標授權並連到上游固定 commit（規則見 [M4](M4-watcom.md)）。文章只寫函式名、符號、參數與回傳值的意義、演算法步驟，
  示意用自己寫的虛擬碼；每次推送前跑外洩閘門，命中就不推。
- **位元組簽章只做 Borland 與 Microsoft**，而且只收 64 bytes 以內、位址與 relocation 已遮罩的短樣式。
  DSMI 的授權禁止逆向該套件，DMX 的權利狀態不明，這兩份只寫原始碼層級的機制。
- **原廠沒附原始碼的部分只寫介面。** Borland 的 8087 模擬器與 graphics library、VC++ 2.0 大部分浮點例程，
  只寫呼叫端看得到的行為。
- **法律問題不自行下結論。** 條款的適用範圍、DMX 目前的權利人查不到一手來源時，寫「待查證」。

## 每一項怎麼推進

1. 照 milestone 順序，挑依賴已滿足、編號最小的未完成項。
2. 研究項目：盤點建置檔 → 讀原始碼 → 對拍 → 寫研究筆記，每條結論標推論等級（已證實／強推論／假說／未知）。
3. 公開項目：依 `CLAUDE.md` 的文章格式寫成文章，配 SVG 圖。
4. 外洩閘門 → 專家與學生兩個審查 → 查證並套用審查意見。
5. `tools/worklist.py` 確認該條已不成立 → commit（訊息寫 `Closes #N`）→ push。
6. 做到一半發現新問題（例如對拍出現解釋不了的差異），不在原項目裡無限延伸：記下已排除的假設，另開一條 worklist 與 issue。

## 整體完成條件

- M1、M2 的 issue 全部關閉，各篇文章通過外洩閘門與審查。
- 讀者照 M2 的文章與簽章，能把一支 BC++ 2.0 編譯的 DOS 程式裡的函式庫函式標出來，並判斷它用的記憶體模型；
  簽章有附正對照的命中率。
- M3 的研究項目完成，並為 VC++ 1.0、DMX、DSMI 各登記至少一篇文章的 issue。
- M4 第一批：6.5 與 7.0 的素材與盤點到位，6.5 的 runtime 文章通過審查。
  整個 M4 完成時，讀者能從執行檔判斷大約是哪一代 Watcom 工具鏈。
