# 拿到一支 Watcom 編譯的程式，怎麼判斷是哪一代

## 結論

前面三篇分別拆了 6.5（1988，16 位元）、7.0（1989，第一代 32 位元）與 9.01（1992，DOS/4GW 年代）。
這一篇把它們收成一張判斷表。

最快的三個問題，依序問下去通常就夠了：

1. **符號尾端有沒有一個底線？** 有，就是 Watcom 的暫存器呼叫慣例（`strlen_`、`main_`）。
   沒有但有一整排前置底線的函式，可能是它的堆疊慣例版本，或根本不是 Watcom。
2. **程式是 16 位元還是 32 位元？** 看段的定址寬度與指標大小。
3. **有沒有那組 far 指標 helper（`__PTS`、`__PTC`、`__PIA`、`__PCA`）？**
   有就是 16 位元那一代——**這組符號是分水嶺**。
   但它只能單向用：**沒看到不代表是 32 位元**，可能只是那支程式沒做過 far 指標運算。

## 判斷表

| 特徵 | 6.5（1988） | 7.0（1989） | 9.01（1992） |
|---|---|---|---|
| 位元寬度 | 16 | 32 | 32 |
| 記憶體模型 | 六種（位元旗標組合） | flat | flat |
| 執行環境 | 純 DOS | Phar Lap 或 A.I. Architects，**自己買** | DOS/4GW **隨附**，另支援 Phar Lap 與 Ergo |
| 函式符號 | `strlen_` | `strlen_` | `strlen_` |
| 指標 helper `__PTS`／`__PTC`／`__PIA`／`__PCA` | **有**（程式用到才連進來） | 沒有 | 沒有 |
| 32 位元乘除 helper `__I4M`／`__I4D` | **有** | 沒有 | 沒有 |
| 堆疊檢查 `__STK` | 有（可用編譯選項關掉） | 有 | 有 |
| 浮點轉換 `__I4FS`／`__ModF` | 有 | 有 | 有 |
| `__StartTime`（給 `clock` 用） | 沒有 | **有** | 有 |
| 程式碼段名 | medium 是 `CLIBM_TEXT`；large／huge 是「模組名＋`_TEXT`」 | （庫解不開） | （庫解不開） |
| 啟動碼向 DOS 歸還記憶體（`AH=4Ah`） | **有** | 沒有 | （讀不到） |
| 空指標哨兵檢查 | **有**（除 tiny 外五個模型） | 沒有 | （讀不到） |
| `int 31h`（DPMI 呼叫） | 不可能有 | 沒看到 | 同年代的程式（如 DMX）大量使用 |
| 執行檔結構 | 單純的 MZ | 交給 extender 的連結器決定 | 16 位元 stub ＋ 32 位元本體 |

**表裡標「讀不到」的格子**是這一系列最大的缺口：9.01 磁片上的檔案用 Watcom 自家的壓縮封裝，
我們的解碼器還沒寫完（見最後一節）。

## 三個最有用的判準

### 一、指標 helper 的有無

16 位元的 Watcom 有一整組 helper 處理 far 指標：兩個指標相減、比較、指標加減整數
（依指標放在哪組暫存器分成兩套）。理由是段與位移讓同一個位址有多種寫法，不先正規化就不能比大小。

32 位元 flat 模型沒有段，指標就是整數，這些 helper 整組消失。同樣消失的還有 32 位元乘除——
386 有原生指令。

**所以看到 `__PTS`／`__PIA` 就是 16 位元那一代**，而且這個判準比「指標大小」好用：
指標大小要先正確判斷段的定址寬度，符號名則是直接讀得到的。

### ⚠ 這個判準只能單向用

helper 是**按需連結**的：程式沒做 far 指標的減法或比較，連結器就不會把那個模組拉進來。
所以：

- **看到 `__PTS`／`__PIA` → 可以斷定是 16 位元那一代。**
- **沒看到 → 什麼都不能斷定。** 可能是 32 位元，也可能是一支根本沒碰 far 指標運算的 16 位元程式
  （small 模型的程式尤其容易整組都沒有）。

同樣的道理也適用於 `__STK`：它是編譯器在函式開場插入的檢查，而堆疊檢查是**可以關掉的編譯選項**。
沒看到 `__STK` 不代表不是 Watcom，只代表那支程式編的時候關掉了它。

**能單向用的判準仍然有價值**，只是要記得它答的是「是」而不是「不是」。
真的沒看到任何 helper 時，退回去看啟動碼那兩件事與執行檔結構。

### 二、啟動碼做不做那兩件事

16 位元版的啟動碼會把多出來的記憶體還給 DOS（`AH=4Ah`），並在程式結束時掃一段哨兵看有沒有
被空指標寫壞。32 位元版兩件都不做——記憶體歸 extender 管，而保護模式本身會攔截對位址 0 的寫入。

反組譯時的具體形態：進入點附近如果有 `AH=4Ah` 接著 `AH=30h`（取 DOS 版本），那是 16 位元那一代。

### 三、執行檔的形狀

- **6.5**：普通的 MZ 執行檔。
- **7.0**：Watcom 自己不含連結器，執行檔長什麼樣由 extender 的連結器決定（我們沒有那些工具，
  所以這格是空的）。
- **9.01 以後**：典型的形態是「16 位元的 stub ＋ 32 位元本體」黏在一起，
  stub 負責找到 extender 再把自己交出去。那個年代的遊戲啟動時顯示的 DOS/4GW 字樣就來自這一層。

## 年代之外還能看出什麼

**呼叫慣例**：從 7.0 起，同一套函式庫出暫存器版與堆疊版兩份，檔名帶 `r` 或 `s`。
所以看到 `_r`／`_s` 結尾的 DOS 函式庫檔名（例如 1993 年的音效函式庫 DMX 的兩個庫），
多半是這條線上的東西。**但「`s` 走堆疊」這件事原廠文件沒有明說**，
是從旗標與命名推的（見 [6.5 那篇](watcom65-runtime.md) 的證據段）。

**編譯器本身的位元寬度**：7.0 的編譯器與反組譯器都是 16 位元的 MZ 執行檔，
只是產生 32 位元的碼。「32 位元編譯器」講的是輸出，不是工具自己。

## 這一系列的證據強度，逐版不同

這點對讀者怎麼採信結論很重要：

| 版本 | 有什麼 | 最強的結論等級 |
|---|---|---|
| 6.5 | 原廠文件、**啟動碼原始碼**、函式庫可解開並逐模組反組譯 | 已證實（實測） |
| 7.0 | 原廠文件、**啟動碼原始碼**、編譯器可在無頭 DOS 執行器裡實跑 | 已證實（實測） |
| 9.01 | 原廠安裝腳本、封包成員清單 | 已證實（原文），內容層面**只到檔名與大小** |

9.01 那一欄的限制來自 WPK 封裝還沒解開。所以本篇表格裡凡是 9.01 的機制敘述，
若不是來自安裝腳本，就是從同年代的程式（DMX）推的。

## 證據與未知

**已證實（實測）**：6.5 與 7.0 的符號統計、helper 的有無與語意、段名規律、
7.0 自己編出來的程式長什麼樣。方法是自寫的 OMF 解析器、原廠反組譯器，
以及在無頭 DOS 執行器裡實際編譯。

**已證實（原文）**：三版的記憶體模型與函式庫分份、7.0 的 extender 依賴與兩種呼叫慣例、
9.01 支援的三家 extender 與 DOS/4GW 隨附、啟動碼做與不做哪些事（6.5 與 7.0 有原始碼）。

**強推論**（全篇最弱的一級）：

- 9.01 的啟動碼行為（那兩格「讀不到」）與它是否走 DPMI——推自同年代的 DMX 與安裝腳本。
- 「`s` 版走堆疊」——原廠文件沒明說。
- 「7.0 的執行檔形狀由 extender 的連結器決定」——我們沒有那些連結器，沒有實物可看。

**未知**：

- **9.01 的封包內容解不開**，所以表裡三格是空的。卡點：照原始碼移植的解碼器輸出長度正確
  但內容是亂碼；已排除排序順序這個假設（照原廠的 `qsort` 完整移植後結果沒變），
  剩下三個可疑處寫在私有筆記裡。
- **8.0 沒有取得**，7.0 到 9.01 之間的變化是跳著看的。
- 9.5 與更後面的版本沒碰。
- 沒有任何一版做過位元組簽章（Watcom 這一階段不做），所以這篇的判準全部是符號與結構層級，
  不是位元組層級。
