# 拿到一支 Watcom 編譯的程式，怎麼判斷是哪一代

## 結論

前面三篇分別拆了 6.5（1988，16 位元）、7.0（1989，第一代 32 位元）與 9.01（1992，DOS/4GW 年代）。
這一篇把它們收成一張判斷表。

判斷分兩段走，因為**前三題只分得出「16 位元」與「32 位元」，分不出 32 位元的兩代**：

**第一段：是不是 Watcom、是哪一邊**

1. **符號尾端有沒有一個底線？** 有，就是 Watcom 的暫存器呼叫慣例（`strlen_`、`main_`）。
   沒有的話還不能排除 Watcom：它的堆疊慣例版本不加尾端底線。
   四份出貨庫都逐符號對照過：暫存器版的函式名帶尾端底線，堆疊版的同名函式是裸名
   （少數介面符號如 `_cstart_`、`__fprem_` 兩種慣例下同名，證據細節見表後）。
   注意別拿 `printf_` 當反證：可變參數的函式沒辦法用暫存器慣例，它連進暫存器版也走堆疊——
   底線標的是「連進哪個庫」，不是每個函式的參數怎麼傳。
2. **有沒有那組 far 指標 helper（`__PTS`、`__PTC`、`__PIA`、`__PCA`）？**
   有就是 16 位元那一代（6.5）——**這組符號是分水嶺**，而且只要讀符號名就看得到。
   但它只能單向用：**沒看到不代表是 32 位元**，可能只是那支程式沒做過 far 指標運算。
3. **沒有那組符號時的退路：看位元寬度。** 反組譯畫面上是 16 位元還是 32 位元的暫存器與指令
   （`EAX` 這類 32 位元暫存器、`66h`／`67h` 前綴的有無），以及執行檔標頭。
   這一題比較費工，所以排在第二題之後當備援，不當主線。

**第二段：32 位元的兩代怎麼分**

4. **執行檔開頭有沒有一段 16 位元的 stub，而且字串裡出現 DOS/4GW？**
   有就是 9.01 那個年代（1992 以後）。7.0 沒有這種形態——它連連結器都不含，
   執行檔由 Phar Lap 或另一家的工具產生，格式跟著那家走。
   輔助線索：`int 31h`（DPMI）呼叫在 9.x 年代的程式裡很常見，7.0 那一代還是各家私有介面。

換句話說：**前三題把程式分進「6.5」或「32 位元的某一代」，第四題才分開 7.0 與 9.01。**

## 判斷表

| 特徵 | 6.5（1988） | 7.0（1989） | 9.01（1992） |

| 位元寬度 | 16 | 32 | 32 |
| 記憶體模型 | 六種（由四個位元旗標組合出來） | flat（平坦：沒有段，指標就是 32 位元整數） | flat |
| 執行環境（DOS extender：讓 DOS 程式切進 32 位元保護模式的執行期元件，編譯器本身不含） | 純 DOS，不需要 | Phar Lap 或 A.I. Architects，**自己買** | DOS/4GW **隨附**；安裝程式另問 Phar Lap 與 Ergo，而**啟動碼還多認得 Intel Code Builder**（見 [DPMI 與 DOS/4GW](dos4gw-startup.md)）|
| 函式符號 | `strlen_` | `strlen_` | `strlen_` |
| 指標 helper `__PTS`／`__PIA` | **有**（程式用到才連進來） | 沒有（逐符號） | 沒有（逐符號） |

| 32 位元乘除 helper `__I4M`／`__I4D` | **有** | 沒有（逐符號） | 沒有（逐符號）|
| 堆疊檢查 `__STK` | 有 | 有（`STK` 模組） | 有（`stk` 模組） |
| 浮點轉換 `__I4FS`／`__ModF` | 有 | 有（`IFS`／`AMODF` 模組） | 有（`ifs`／`amodf` 模組） |
| `__StartTime`（給 `clock` 用） | 沒有 | **有** | **又沒有了** |
| 程式碼段名 | medium 是 `CLIBM_TEXT`；large／huge 是「模組名＋`_TEXT`」 | `_TEXT`（全部模組同一個） | `_TEXT`（另各有一個 `BEGTEXT` 與 `_TEXT16` 模組） |
| 啟動碼向 DOS 歸還記憶體（`AH=4Ah`） | **有**（一律做） | 沒有 | 只在 Intel Code Builder 那條路徑上做 |
| 空指標哨兵檢查 | **有**（除 tiny 外五個模型） | 沒有 | 沒有（哨兵資料還在，但不掃描） |
| extender 怎麼決定 | 不適用 | 編譯期 `ifdef` 二選一 | **執行時偵測**，記在 `__Extender`（六個值）|
| 初始化／收尾表的段名 | — | `BCSD`、`_emu_init_*`、`EXEC_*` | `XIB`／`XI`／`XIE`、`YIB`／`YI`／`YIE`（靠連結器按名稱排序拼成一張函式指標表）|
| `int 31h`（DPMI：保護模式程式向 extender 要服務的標準介面） | 不可能有 | 沒看到 | 同年代的程式（DMX）大量使用；**9.01 的啟動碼自己不呼叫**，它用 `int 21h` 偵測 extender |
| 執行檔結構 | 單純的 MZ（DOS 執行檔開頭那兩個字母） | 交給 extender 的連結器決定 | 16 位元 stub（前導小程式，負責找到 extender 再交出控制權）＋ 32 位元本體 |

9.01 那一欄的來源分兩種，強度不同（表格格子裡的括號是證據的取得方式或定義該符號的模組名，
「逐符號」的意義見下面第二點）：

- **啟動碼那幾列讀的是原始碼**（`cstart3r.asm`、`cstart3s.asm`、`cmain386.c`，
  與 7.0 的對應檔逐行對照）：extender 偵測、`__StartTime`、`AH=4Ah`、空指標哨兵、段名。
- **helper 那幾列是逐符號的清單**（類比 `nm` 的輸出：哪些名稱是定義、哪些是外部參照，
  分得開）。7.0 與 9.01 的出貨函式庫是 Phar Lap 的 Easy OMF-386 變體
  （OMF 是 Object Module Format，DOS 時代目的檔與函式庫的封裝格式；這個變體與標準版的
  差異見下方「證據強度」一節），解析器已支援：7.0 兩份庫各 378 個定義符號、
  9.01 各 563 個，每筆記錄都通過 OMF 校驗和（這代表解析器把位元流切對了，是方法驗證）。
  格子裡的「沒有」都是「無定義、也無外部參照」。

**`__StartTime` 那一格原本是照「7.0 有，9.01 應該也有」推的，讀到原始碼才發現 9.01 又拿掉了**；
`AH=4Ah` 也不是單調演進（6.5 一律做、7.0 不做、9.01 只對一家做）。
兩個都提醒同一件事：**相鄰版本的外推在這條線上不可靠**。

## 三個判準背後的道理

上面那四題是操作順序；這一節講的是**每個判準為什麼成立**——知道道理才知道它什麼時候會失效。

### 一、指標 helper 的有無

16 位元的 Watcom 有一整組 helper（編譯器自動插入的輔助函式，原始程式碼裡看不到它）
處理 far 指標：兩個指標相減、比較、指標加減整數
（依指標放在哪組暫存器分成兩套）。理由是段與位移讓同一個位址有多種寫法，不先正規化就不能比大小。

32 位元 flat 模型沒有段，指標就是整數，這些 helper 整組消失。同樣消失的還有 32 位元乘除——
386 有原生指令。

**所以看到 `__PTS`／`__PIA` 就是 16 位元那一代**，而且這個判準比「指標大小」好用：
指標大小要先正確判斷段的定址寬度，符號名則是直接讀得到的。

### ⚠ 這個判準只能單向用

helper 是**按需連結**的：程式沒做 far 指標的減法或比較，連結器就不會把那個模組拉進來。
所以：

- **看到 `__PTS`／`__PIA` → 可以斷定是 16 位元那一代。**
- **沒看到 → 什麼都不能斷定。** 可能是 32 位元，也可能是一支根本沒碰 far 指標運算的 16 位元程式
  （small 模型的程式尤其容易整組都沒有）。

**能單向用的判準仍然有價值**，只是要記得它答的是「是」而不是「不是」。
真的沒看到任何 helper 時，退回去看啟動碼那兩件事與執行檔結構。

（`__STK` 是編譯器在函式開場插入的，照理也會受編譯選項影響，
但手上這兩版的原廠文件裡**沒有找到**停用堆疊檢查的開關，所以這裡不下斷言。）

### 二、啟動碼做不做那兩件事

16 位元版的啟動碼會把多出來的記憶體還給 DOS（`AH=4Ah`），並在程式結束時掃一段哨兵看有沒有
被空指標寫壞。32 位元版兩件都不做。記憶體歸 extender 管，所以沒有還給誰的問題；
至於為什麼不再檢查空指標，合理的解釋是保護模式本身會攔截對位址 0 的寫入——
**這是推論，原廠沒說**。

反組譯時的具體形態：進入點附近如果出現「`AH` 設成 `4Ah` 再 `int 21h`」，接著不遠處又有
「`AH` 設成 `30h` 再 `int 21h`」（取 DOS 版本），那是 16 位元那一代。
（`int 21h` 是 DOS 的系統呼叫入口，功能編號放在 `AH`。）

### 三、執行檔的形狀

- **6.5**：普通的 MZ 執行檔。
- **7.0**：Watcom 自己不含連結器，執行檔長什麼樣由 extender 的連結器決定（我們沒有那些工具，
  所以這格是空的）。
- **9.01 以後**：典型的形態是「16 位元的 stub ＋ 32 位元本體」黏在一起，stub 負責找到 extender
  再把自己交出去。stub 的原始碼（`wstub.c`，984 bytes）解出來了：它用 `_searchenv`
  在 `DOS4GPATH` 與 `PATH` 裡找 `dos4gw.exe`，然後用 `execvp` 把自己換掉，
  並把自己的路徑當參數傳過去讓 extender 回頭讀本體。
  **不過我們沒有反組譯實際編出來的 stub**，所以「執行檔開頭那段就是它」仍是推論。
  那個年代的遊戲啟動時常見 DOS/4GW 字樣，是一般印象，本系列沒有做過遊戲清單普查。

## 年代之外還能看出什麼

**呼叫慣例**：從 7.0 起，同一套函式庫出暫存器版與堆疊版兩份，檔名帶 `r` 或 `s`。
所以看到 `_r`／`_s` 結尾的 DOS 函式庫檔名（例如 1993 年的音效函式庫 DMX 的兩個庫），
多半是這條線上的東西。**但「`s` 走堆疊」這件事原廠文件沒有明說**，
是從旗標與命名推的（見 [6.5 那篇](watcom65-runtime.md) 的證據段）。

**編譯器本身的位元寬度**：7.0 的編譯器與反組譯器都是 16 位元的 MZ 執行檔，
只是產生 32 位元的碼。「32 位元編譯器」講的是輸出，不是工具自己。

## 這一系列的證據強度，逐版不同

這點對讀者怎麼採信結論很重要：

下表的「最高等級」指**各版目前能達到的天花板**，不是整篇文章的評級——
依本庫的規範，文章前置欄位的 `evidence` 取全篇**最弱**的一級，所以那幾篇標的都是「強推論」。

| 版本 | 有什麼 | 最高等級 |
|---|---|---|
| 6.5 | 原廠文件、**啟動碼原始碼**、函式庫可解開並逐模組反組譯 | 已證實（實測） |
| 7.0 | 原廠文件、**啟動碼原始碼**、編譯器可在無頭 DOS 執行器裡實跑 | 已證實（實測） |
| 9.01 | 原廠文件與安裝腳本、**啟動碼與 stub 的原始碼**（磁片封裝已解開）| 已證實（原文） |

三代現在都有啟動碼的原始碼可讀；**函式庫那一層在三代也都能逐符號讀**，差別在方法：

1. **6.5 的函式庫是標準 OMF**，逐模組反組譯過，它那一欄的 helper 有
   371 個公開符號的分類統計（267 尾端底線、98 前置底線、6 個兩者皆非）。
2. **7.0 與 9.01 的函式庫是 Easy OMF-386 變體**：`.LIB` 外層的圖書館封裝照標準走，
   變的是裡面每個模組的記錄——模組開頭一筆 COMENT 記錄（OMF 裡放附註資訊的記錄類型；
   Phar Lap 自定的 class `0xAA`，內容寫 `80386`）標記之後，
   段長與位移類欄位從 2 位元組加寬成 4 位元組。解析器補上這層語意後，
   7.0 得到 255×2 個模組（兩份庫各 255）、378×2 個定義符號，9.01 是 334×2 個模組、563×2 個；
   四份庫共 1,178 個模組的每筆記錄都通過 OMF 校驗和，符號層並與 7.0 原廠反組譯器
   對照過三個模組。表裡標「逐符號」的就是這一類。

另外，表裡與 DPMI 有關的那一列講的是**同年代的應用程式**（DMX），不是 9.01 編譯器本身——
9.01 的啟動碼自己不呼叫 `int 31h`。

## 證據與未知

**已證實（實測）**：6.5 的符號統計（371 個公開符號的三種分類）、helper 的語意與段名規律——
方法是自寫的 OMF 解析器加原廠反組譯器。
7.0 自己編出來的程式長什麼樣，則是在無頭 DOS 執行器裡實際編譯再反組譯得到的。
7.0 與 9.01 的出貨函式庫（Easy OMF-386 變體）現在也有逐符號清單：
定義與外部參照分得開、每筆記錄通過校驗和，符號層並與 7.0 原廠反組譯器對照過三個模組；
表裡標「逐符號」的格子屬於這一類。
「堆疊版的一般函式是裸名」也在這一級：四份函式庫做了全庫掃描，
暫存器版帶尾底線的函式名在堆疊版都有對應的裸名（7.0 成對 277／283、9.01 成對 402／410；
沒對上的少數是 `_cstart_`、`__fprem_`、`_small_code_` 這類**兩種慣例下同名**的介面符號）。

**已證實（原文）**：三版的記憶體模型與函式庫分份、7.0 的 extender 依賴與兩種呼叫慣例、
9.01 支援的三家 extender 與 DOS/4GW 隨附、啟動碼做與不做哪些事（6.5 與 7.0 有原始碼）。

**強推論**（全篇最弱的一級）：

- 「`s` 版走堆疊」——原廠文件沒明說。符號形態的規律（上一段）是實測，
  但「裸名＝參數走堆疊」這個定性仍是從 6.5 的文件與命名推的。
- 「7.0 的執行檔形狀由 extender 的連結器決定」——我們沒有那些連結器，沒有實物可看。
- 「9.01 的執行檔是 stub ＋ 本體」——stub 的原始碼已讀到（`wstub.c`），
  但**沒有反組譯實際編出來的 stub**，所以「執行檔開頭那段就是它」仍是推論。
- 「保護模式會攔截空指標寫入，所以 32 位元版不再檢查」——原廠沒說。

**未知**：

- 7.0 與 9.01 的函式庫已能逐符號讀（Easy OMF-386 變體的語意層已補上），但**逐模組的
  反組譯明細還沒做**（`STK`／`stk` 是僅有的例外），所以 6.5 那篇那種
  「每個 helper 的大小」表，32 位元這邊還沒有。
- ~~8.0 沒有取得~~、~~9.5 與更後面的版本沒碰~~：8.0／8.5a／9.5b 已於 R23 取得並盤點，
  8.0→9.5 的差異見 [8.0 到 9.5](watcom80-delta.md)。
- 沒有任何一版做過位元組簽章（Watcom 這一階段不做），所以這篇的判準全部是符號與結構層級，
  不是位元組層級。
