# conio：一個結構、三個原語、兩條路

## 結論

BC++ 2.0 的 conio 全部狀態放在一個叫 `_video` 的結構裡（視窗四角、目前屬性、螢幕大小、是不是圖形模式、
要不要防雪花、顯示記憶體位址），畫面操作只有三個原語：`__cputn` 寫字元、`__scroll` 捲動或清除、
`__screenio` 搬區塊。每個原語都有兩條路——直接寫顯示記憶體，或走 BIOS 的 `int 10h`——由全域變數
`directvideo` 與「是不是圖形模式」決定。

對 remake 影響最大的幾條：

- **`\n` 只換列不回欄**。conio 的換行不含歸位，`cputs("A\nB")` 的 B 會落在 A 的右下角。
- **`\b` 只把游標退一格，不清掉字元**，而且不會退出視窗左界。
- **捲動範圍是視窗（螢幕上一塊矩形範圍，不是圖形介面的視窗），不是整個螢幕**；
  `clrscr`、`clreol`、`delline`、`insline` 全都是同一個捲動原語的不同參數。
- **兩套座標系並存**：`gotoxy`、`cputs`、`clrscr` 用視窗座標（1 起算、相對視窗），
  `gettext`、`puttext`、`movetext` 用絕對螢幕座標。
- **座標無效時整個呼叫被忽略**，沒有回報，也不會夾到邊界。
- **`_wscroll` 設成 0 之後，寫到視窗右界不會換列**，而是回到同一列的左界繼續蓋。

機制來自原始碼，行為規格來自一支自寫測試程式（[`examples/conio/`](../../examples/conio/)）在五個記憶體模型下、
在 dosgolem 裡的實跑結果（五個模型輸出完全相同，另外比對模擬器 dump 出來的文字畫面）。

## 根本問題

### 文字畫面有兩種寫法，各有各的代價

IBM PC 的文字模式把畫面直接對映到記憶體：每格兩個位元組，低位元組是字元碼、高位元組是**屬性**——
低 4 個位元是前景色（0–15）、接著 3 個位元是背景色（0–7）、最高位元是閃爍旗標，
所以屬性值就是 `背景 << 4 | 前景`，要閃爍再加 128。彩色卡的畫面在 `0xB800`、單色卡在 `0xB000`。
程式可以直接往那裡寫，一格兩個位元組，快得像改一個變數。

BIOS 也提供 `int 10h` 的一整組服務（設游標、寫字元、捲動）。走 BIOS 慢得多——一次呼叫只處理一個字元，
中間還要移動游標——但它在所有相容機器上都能用。

1991 年沒有「一定安全」的選擇：直接寫記憶體會撞上非標準顯示卡與某些相容機，走 BIOS 則慢到不能做動畫。

### 原始 CGA 會在畫面上撒雪花

最早的 IBM CGA 卡，顯示記憶體只有一條匯流排，而顯示控制器必須不停地把內容讀出來送去螢幕。
CPU 這時候寫進去就是在搶同一條線，讀出的資料一半新一半舊，畫面上就閃出白點——當年叫它「snow」。

避開的方法是等**水平回歸**：螢幕上的電子束掃完一列、往回移到下一列起點的那段空檔，
顯示控制器沒在讀記憶體，這時候寫就不會撞。代價是每格都要先去輪詢一個 I/O 埠等那個空檔。

後來的卡（EGA 以後，以及 COMPAQ 的相容機）沒這個問題，等回歸純粹是浪費時間。
所以「要不要等」必須在執行時判斷。

### 遊戲需要視窗

一個文字模式的遊戲畫面通常分成幾塊：地圖、狀態、訊息。每塊各自捲動、各自清除。
如果每個函式都要帶四個角座標，呼叫端會被邊界計算淹沒。

## 推導

### 一個結構裝下整個狀態

`_video` 是個十幾個位元組的結構，欄位全是 `unsigned char` 加一個遠指標（帶著段的 4 位元組指標，
見[一份原始碼怎麼編出五個記憶體模型](memory-model-macros.md)）：視窗的四個邊界、目前屬性、
初始屬性、目前模式、螢幕高與寬、是不是圖形模式、要不要防雪花、顯示記憶體位址。
`gettextinfo` 幾乎就是把它抄一份出來給呼叫端（多附上目前游標位置）。

它由一個掛在啟動表上的函式 `_c0crtinit` 填好，在 `main` 之前跑（見[啟動與結束鏈](startup-and-exit.md)）：

| 欄位 | 怎麼決定 |
|---|---|
| 目前模式、螢幕寬 | 問 BIOS 目前的顯示模式 |
| 初始屬性 | 讀游標所在那格的屬性，**並且把閃爍位元清掉** |
| 是不是圖形模式 | 由模式編號判斷 |
| 螢幕高 | 25，除非是 43／50 列模式（那時讀 BIOS 資料區） |
| 要不要防雪花 | 不是單色卡、BIOS ROM 裡沒有 `COMPAQ` 字樣、而且沒裝 EGA |
| 顯示記憶體位址 | 單色卡 `0xB000`，其餘 `0xB800` |
| 視窗 | 整個螢幕 |

結構裡的視窗邊界是 **0 起算**的；`window`、`gotoxy` 這些對外的函式收 1 起算的座標，進來就減 1 存進去。
兩套編號的差別只在結構內外，呼叫端看到的一律是 1 起算。

那三個條件湊在一起看起來毫無關聯，其實只是在回答一個問題——「這台機器的顯示卡是不是原始的 IBM CGA」。
單色卡沒有這個問題；COMPAQ 的相容機修掉了；EGA 以後的卡也修掉了。剩下的才需要付等回歸的代價。
判斷方式很土（去 ROM 裡找廠商字樣），但它是當年唯一能在執行時問出答案的辦法。

### 三個原語

conio 有三十個函式，但**真正動到畫面內容的只有十個**，而它們全部落到三個原語其中之一：

| 原語 | 做什麼 | 誰用它 |
|---|---|---|
| `__cputn` | 逐字元寫出去，自己管游標與換行 | `putch`、`cputs`、`cprintf`（也是 `printf` 三個輸出函式之一） |
| `__scroll` | 對一個矩形區域上捲或下捲 n 列，**n 為 0 時代表用目前屬性清空** | `clrscr`、`clreol`、`delline`、`insline`，以及 `__cputn` 寫到視窗底部時 |
| `__screenio` | 在顯示記憶體與一般記憶體之間搬一段 | `gettext`、`puttext`、`movetext` |

其餘二十個分成三類：只改 `_video` 狀態的（`textattr` 家族、`gettextinfo`）、只透過 BIOS 設游標或模式的
（`gotoxy`、`window`、`textmode`、`_setcursortype`），以及鍵盤側的（`getch`、`kbhit`、`ungetch`⋯⋯）。
`getche` 與 `cgets` 算半個——它們讀鍵不碰畫面，但回顯那一半會走 `__cputn`。

清除與捲動是同一件事這點值得停一下：BIOS 的捲動服務本來就把「捲 0 列」定義成「用指定屬性填滿區域」，
所以 `clrscr` 只是「對整個視窗捲 0 列」，`clreol` 是「對游標列從游標欄到視窗右界捲 0 列」，
`delline` 是「從游標列到視窗底部上捲 1 列」，`insline` 是同一段下捲 1 列。四個函式，一個原語。

### 兩條路

**這個取捨沒有標準答案，所以 Borland 把它做成一個可以改的全域變數 `directvideo`**，讓呼叫端自己決定要速度還是要相容性。

三個原語都有同一個岔路：**不是圖形模式、而且 `directvideo` 非 0**，就直接存取顯示記憶體；否則走 BIOS。
圖形模式為什麼也要走 BIOS？因為那時候顯示記憶體不再是「一格兩個位元組」的排列，
而是按像素與位元平面擺的——直接寫進去只會得到一堆雜訊，所以無論 `directvideo` 是什麼都得交給 BIOS。

「哪一端是畫面」這個判斷只發生在 **BIOS 路徑**——它拿段值跟 `_video` 裡的顯示記憶體位址比，
決定哪一端要逐格走 BIOS。直接路徑不做這個判斷，它只是一個會避開重疊與雪花的字組搬移。

走 BIOS 那條特別慢：`__screenio` 的 BIOS 版是一格一格處理的——每格先把游標移過去（`AH=02h`），
讀一格用 `AH=08h`、寫一格用 `AH=09h`，整批做完再把游標移回原處。
**每格至少兩次 BIOS 呼叫**，搬一個 80×25 的畫面就是四千次起跳；`movetext` 兩端都在畫面上時每格四次，再翻一倍。

直接寫記憶體那條，在 `_video.snow` 開著時每次存取前要先輪詢 CGA 的狀態埠等水平回歸。

`__scroll` 還有個附帶條件：**只有「捲 1 列」才走直接搬移**，其餘情況（包括捲 0 列，也就是所有的清除）
一律交給 BIOS。所以 `clrscr`、`clreol` 不管 `directvideo` 設什麼都是走 BIOS 的。

**那條直接搬移的路徑在 1991 年的兩次出貨之間改過**，而且是這個函式庫裡唯一一個原始碼與出貨版對不上的模組：

| 版本 | 捲 1 列（`directvideo` 開著）時 |
|---|---|
| 1991-04 | 搬移其餘列，**空出來的那一列保留原本的內容**——填空白的動作寫進了一個堆疊上的區域陣列，沒有人把它寫回畫面 |
| 1991-08 | 同樣搬移，之後把空白寫回空出來的那一列 |

本 repo 手上的原始碼對應 1991-04 版；1991-08 版的模組多引用了兩個區塊搬移函式、程式碼大了 77%。
兩版各自連結一支相同的測試程式實跑過：4 月版捲完之後最後一列殘留舊字，8 月版是空白。
**remake 要照哪一版做，取決於原版遊戲連結的是哪一版函式庫。**

### 游標與換行的規則

`__cputn` 不依賴 BIOS 的游標推進，它自己算：進來時取一次目前欄列，處理完所有字元才把游標寫回去——
**寫回去的是 BIOS 的游標位置，也就是畫面上那個會閃的游標**，所以一次 `cputs` 只移動一次游標。
每個字元的規則是：

| 字元 | 做什麼 |
|---|---|
| `\a` | 走 BIOS 的 TTY 輸出（就為了那一聲） |
| `\b` | 欄減一，**不清字元**，不會退過視窗左界 |
| `\r` | 欄回到視窗左界 |
| `\n` | **列加一，欄不動** |
| 其他 | 寫一格（含目前屬性），欄加一 |

寫完之後檢查兩件事：欄超過視窗右界時，欄回左界、列加上 `_wscroll`；列超過視窗底部時，
對視窗上捲一列、列退回去。

`_wscroll` 預設是 1。把它設成 0，第一個檢查裡的「列加上 0」等於不換列——結果是**游標回到同一列的左界繼續寫**，
後面的字元把前面的蓋掉。這正是那個年代做狀態列的手法：不希望一個太長的字串把整個畫面頂上去。

### 鍵盤那一半與 `textmode`

這幾支常被一起用到，機制單純但細節容易踩：

| 函式 | 行為 |
|---|---|
| `getch` | 走 DOS 而不是 BIOS，完全不碰 `_video`，不回顯 |
| `getche` | 就是 `putch(getch())`——回顯那一半才進 `__cputn`，所以吃目前視窗、屬性與 `_wscroll` |
| `cgets` | 緩衝區第 0 個位元組**由呼叫端填「最多幾個字元」**，回來時第 1 個位元組是實際讀到幾個、字串從第 2 個位元組起算並補 `\0`，回傳值指向那裡。實際可存 `s[0] − 1` 個字元；只認 `\r` 結束，不吃換行、也不補換行。退格會送出「退格、空白、退格」三個字元，**真的把畫面上的字抹掉**（與 `__cputn` 收到裸退格時不清字元剛好相反），左方向鍵也當退格 |
| `getpass` | **完全不走 conio 的畫面路徑**：提示字串走 `stderr`，讀鍵與換行直接呼叫 DOS，最多 8 個字元，存在一塊靜態緩衝區（下次呼叫就覆蓋） |
| `textmode` | 換模式之後**整份重推** `_video`（模式、螢幕寬高、是不是圖形模式、要不要防雪花、顯示記憶體位址），**視窗重設成整個螢幕**，目前屬性回到初始屬性。它不會重讀畫面上那格的屬性，所以初始屬性維持程式啟動時的值 |

## 在執行檔裡怎麼認

| 看到 | 推論 |
|---|---|
| 一支小函式：`push bp`／`push ds`、把 `DS` 設成 `0x40`（BIOS 資料區）、對 `AH` 等於 `00h` 與 `0Fh` 做特判，其餘直接 `int 10h` | conio 的 `int 10h` 共用入口。認出它就同時認出整個 conio 與 `_video` |
| 一個 15 位元組的全域結構：前四個位元組是視窗四角、`+4` 目前屬性、`+5` 初始屬性、`+6` 模式、`+7` 螢幕高、`+8` 螢幕寬、`+9` 是不是圖形模式、`+10` 防雪花、`+13` 是 `0xB800` 或 `0xB000` | `_video` |
| 測 `_video+9` 那個位元組，再測一個獨立的 `int`（初值 1，在已初始化資料段），然後二選一 near call | 三個原語之一的岔路；那個 `int` 是 `directvideo` |
| 四支小函式各自推六個參數（方向、四個座標、列數）給同一支函式，其中方向是常數 6 或 7、列數是 0 或 1 | `clrscr`／`clreol`／`delline`／`insline` 在呼叫 `__scroll`（常數在呼叫端，不在 `__scroll` 本體） |
| 一段迴圈輪詢埠 `0x3DA`、測某個位元、寫一格顯示記憶體 | 防雪花的直接寫入路徑 |
| 啟動表裡一個優先度 16 的項目，指向的函式開頭把 `0Fh` 放進 `AH` 再 near call | `_c0crtinit`（填 `_video` 的那支） |
| 讀 `F000:FFEA` 起的位元組並與字串比較 | 雪花偵測裡的 COMPAQ 判斷 |

容易誤判的地方：

- **直接寫顯示記憶體的程式碼不一定是 conio**：很多遊戲自己寫一套。判準是它有沒有跟 `_video` 這個結構互動。
- **`cprintf` 與 `printf` 走的是同一個格式化引擎**，差別只在輸出函式（見 [printf 家族](printf-engine.md)），
  所以看到格式化程式碼呼叫一個會碰 `_video` 的輸出函式，那是 `cprintf`。
- 這一節的特徵是從機制推得的，還沒有逐一在第三方程式上驗證。

## 給 remake 的行為規格

實測條件：`examples/conio`，五個記憶體模型（輸出完全相同），在 dosgolem 執行，模式 3（80×25 彩色），
連結的是 1991-08 版函式庫。`directvideo` 預設是 1，其中一段另外把它設成 0 重跑，兩條路結果相同。

### 視窗與游標

| 情況 | 結果 |
|---|---|
| 程式啟動時的視窗 | 整個螢幕（1, 1, 80, 25） |
| `window(10, 5, 40, 15)` 之後 | 游標跳到視窗的 (1, 1) |
| `gotoxy(3, 2)` | 視窗座標，對應螢幕的 (12, 6) |
| `gotoxy(100, 100)`（越界） | **整個呼叫被忽略**，游標不動 |
| `gotoxy` 的越界檢查 | 在 8 位元上做的，所以座標差 256 的倍數會繞回來被當成合法值（`window` 用的是 `int`，沒這個問題） |
| `window(1, 1, 200, 200)`（越界） | **整個呼叫被忽略**，視窗不變 |
| `wherex()`／`wherey()` | 回傳的是視窗座標，1 起算 |

### 寫字元

以下在一個 10 欄 × 4 列的視窗裡測：

| 寫什麼 | 結果 |
|---|---|
| `"AB"` 從 (1,1) 開始 | 游標到 (3,1)，兩格分別是 `A`、`B` |
| `"XY\nZ"` 從 (1,1) 開始 | 游標到 (4,2)——**`Z` 落在第 3 欄**，不是第 1 欄 |
| `"\r"` | 游標回到欄 1，列不變 |
| 在 (1,1) 寫 `"\b\b"` | 游標留在 (1,1)，畫面不變 |
| 從 (1,2) 寫滿 10 欄 | 游標到 (1,3) |
| 在最後一列寫滿 | 視窗上捲一列，原本第一列的內容消失，游標留在最後一列的欄 1 |
| `_wscroll = 0` 時寫 13 個字元到 10 欄寬的視窗 | 游標到 (4,1)：**不換列，回到同一列左界蓋掉前面三格** |

### 兩條路的結果

| 情況 | 結果 |
|---|---|
| 同樣的 `cputs` 在 `directvideo = 1` 與 `0` 下 | 畫面上的字元與屬性**完全相同** |
| `directvideo = 0` 時的 `clrscr` 與視窗捲動 | 與直接寫顯示記憶體時相同 |

差別只在速度與相容性，不在結果——這正是那個開關能存在的前提。

### 屬性

| 情況 | 結果 |
|---|---|
| `textcolor(LIGHTGREEN); textbackground(BLUE)` | 屬性值 26 = `10 + (1 << 4)` |
| `textattr(BLINK + YELLOW + (RED << 4))` | 屬性值 206 = `128 + 14 + (4 << 4)` |
| `clrscr()` | 用**目前**屬性填空白（字元 32） |
| 程式啟動時的屬性 | 讀畫面上游標那格、清掉閃爍位元；**值隨執行環境而定**（dosgolem 下是 0） |

### 區塊操作

| 情況 | 結果 |
|---|---|
| 座標 | **絕對螢幕座標**，不受目前視窗影響 |
| `gettext` 的緩衝區 | 一列接一列，第二列從第「寬」格開始；大小 = 寬 × 高 × 2 bytes；每格低位元組是字元、高位元組是屬性 |
| `gettext`／`movetext` 座標越界 | 回 0，什麼也不做 |
| **`puttext` 座標越界** | **回 1，照寫**——它根本不驗座標。實測把最後一列右緣外的兩格寫進了顯示記憶體 |
| 座標檢查只擋上界 | 三個函式的檢查都只比螢幕寬高與「起點是否大於終點」，**0 與負座標通過**，位址會算到畫面起點之前 |
| `movetext` 區域重疊 | 列方向有處理（目的列比來源列大時由下往上搬）；同一列內的水平重疊靠搬移函式自己判斷方向 |

## 證據與未知

除了 `SCROLL` 那一個模組以外，本篇引用的 conio 模組都對拍過：以原廠工具鏈重編，在五個記憶體模型下
與 1991-04、1991-08 兩份出貨庫逐位元組相同。

| 結論 | 出處 | 等級 |
|---|---|---|
| `_video` 的欄位與用途、欄位位移 | RTL 的 `_VIDEO.H` | 已證實（原文） |
| 三個原語的分工與兩條路的岔路條件 | RTL 的 `SCREEN.C`、`VRAM.CAS`、`CPRINTF.C` | 已證實（對拍） |
| **`__scroll` 直接搬移路徑的內部做法** | RTL 的 `SCROLL.C` **只對應 1991-04 版**；1991-08 出貨版與原始碼不同（外部參照與大小都不一樣），該版行為由反組譯與兩版實跑確認 | 已證實（原文＋反組譯＋實跑），**版本相依** |
| 清除＝捲 0 列；`clreol`／`delline`／`insline` 都是 `__scroll` 的參數變化 | RTL 的 `CLRSCR.C`、`CLREOL.C`、`INSLINE.C` | 已證實（對拍） |
| `__cputn` 的逐字元規則與 `_wscroll` | RTL 的 `CPRINTF.C`、`WSCROLL.C` | 已證實（對拍） |
| 兩套座標系、`gettext` 的緩衝區形狀、`puttext` 不驗座標、`movetext` 的重疊處理 | RTL 的 `GPTEXT.C`、`MOVETEXT.C`、`SCREEN.C` ＋ `examples/conio` 的越界實測 | 已證實（對拍＋實測） |
| `_video` 的初始化與雪花偵測條件、結構內部用 0 起算的視窗邊界 | RTL 的 `CRTINIT.CAS`、`WINDOW.C` | 已證實（對拍） |
| 鍵盤那一半與 `textmode` 的行為 | RTL 的 `GETCH.CAS`、`CGETS.C`、`GETPASS.C`、`TEXTMODE.C` | 已證實（對拍） |
| 屬性的位元編碼與色號 | 出貨的 `conio.h`、RTL 的 `COLOR.C` | 已證實（對拍） |
| 行為規格各條 | `examples/conio` × 五個模型，在 dosgolem 執行 | 已證實（實測） |
| 辨識特徵 | 由機制推得，未逐一在第三方程式上驗證 | 強推論 |

未知：

- **BIOS 路徑只驗了寫字元與清除**（結果與直接寫顯示記憶體相同）。**捲 1 列**的 BIOS 版本、
  以及 BIOS 版的區塊搬移（逐格讀寫那條）沒有實跑——後者在不支援 `AH=08h` 的環境會整批出錯。
- **1991-08 版 `__scroll` 的直接路徑**已由反組譯與實跑確認會清空騰出來的那一列，
  但本 repo 沒有那一版的原始碼，細節（例如它讀回的範圍）只能從反組譯推。
- **啟動時的屬性那一列不構成證據**：dosgolem 的畫面初始屬性是 0，
  「有沒有讀畫面」與「有沒有清掉閃爍位元」四種可能的輸出完全一樣。機制只有原文證據。
- **文字畫面 dump 覆蓋的是區塊操作、多列讀取、`_wscroll = 0` 的覆寫、越界寫入與 BIOS 路徑**；
  換行與捲動的畫面結果是用 `gettext` 單格取值驗的，而 `gettext` 自己也是受測對象。
- **雪花那條路完全沒測**：dosgolem 沒有 CGA 的狀態埠行為，等回歸的迴圈在模擬器裡是空轉。
- 43／50 列模式、單色卡、40 欄模式都沒測。
- Microsoft C 的對應做法要等 M3。
